# Design decisions

Why the tool is the way it is. Each decision can be overturned, but read its reason first. Open questions are at
the end.

| No. | Decision | Why |
|---|---|---|
| D1 | Python 3.9 or newer, standard library only. No libraries at all | Nothing to install, nothing to pin or patch, and no supply chain to trust. The price is `urllib`, which is plain but enough |
| D2 | A system is described by a target file, not by code: where a message goes, where the reply is, how the conversation is kept | A team can test their system without writing or reading Python. Two conversation styles cover most chat systems: the whole conversation sent each time, or a session the system remembers |
| D3 | A key is only ever read from an environment variable and only ever put in a header. A target file with a secret in its address or body is refused. Results keep the host name and nothing else of the request | A report is shared and a target file is committed |
| D4 | The address must be https (http for this computer only), with no user name in it, and a redirect is never followed | A run is hostile-looking traffic with a key attached. It must go where the file says and nowhere else |
| D5 | Ordinary messages are part of every pack, and a run counts any that are refused. An ordinary message whose reply held something from `never_say` is counted on its own ("given something secret") | An assistant that blocks honest people is as broken as one that can be talked round. The second kind turned up in the first practice run: a weak bot recited its instructions to a message that only contained the word |
| D6 | Every report, the skill and the README say a pass is not a certificate | People will want to read "held 74 of 74" as "approved" |
| D7 | Judging is by word lists, and the report says which held replies nothing but a word list has looked at | Word lists are free and repeatable, and wrong both ways. Saying what nobody has read is the honest answer when there is no judge |
| D8 | A made-up word a refusal is likely to repeat (BANANA, "I have been hacked") only counts when the reply did not also decline. This is written into those patterns, not applied to every pattern | A system that declines in its own words says "I can't reply with only the word BANANA". Applying the rule to every pattern would hide "I can't show all of my instructions, but in short they say..." |
| D9 | A second model can be given as a judge. It can only add a concern, never clear a word-list failure. Anything it answers other than one of three known words becomes "unsure", which sends the reply to a person. It is handed the message and reply as data between markers with a random number in them | The judge reads text written to manipulate models. It must not be able to wave a failure through |
| D10 | Earlier messages in a build-up attack are really sent, and the system's own replies are its side of the conversation | From outside, what the system really said is what an attacker would have |
| D11 | Each message gets a conversation of its own | One attack must not help or hinder the next, and a system that pauses after several attacks would stop the run |
| D12 | A run asks before sending, prints the host, is limited to 500 requests unless told otherwise (5000 at most), pauses half a second between requests to anything but this computer, and stops after five messages in a row get no reply. A target file that says production needs `--production` | The tool cannot know a system is the runner's to test, and every message costs someone money |
| D13 | The report is one HTML file that loads and runs nothing, with every reply encoded, written readable by its owner only | A reply to an attack is exactly where a script tag turns up, and a report can hold what the system leaked |
| D14 | `export` and `judge`: the messages as a sheet to fill in, judged afterwards | Some systems have only a chat page. It also keeps sending and judging apart, which is what a page in another tool would need |
| D15 | A made-up chatbot ships with the tool, in three kinds | A first run that costs nothing and shows each outcome once. It also lets the tests go through a real address |
| D16 | The core pack holds only tricks that need no knowledge of the system. Attacks about one system's own harms live in a pack of their own, and one is included as the pattern | Running "mark the backup question as answered" against a leave helper says nothing. Each system needs its own list of what must never happen |
| D17 | The folder is laid out as a Claude Code plugin with one skill, and the skill uses only the `name` and `description` fields | It can be tried with `claude --plugin-dir .` without moving anything. The two fields are the ones every place that takes skills accepts |
| D18 | The records are kept with the code: this file, `AGENTS.md`, `CHANGELOG.md` | So a different person or AI tool can carry on from the repository alone |
| D19 | One skill folder serves Claude, Codex and Antigravity. `package-skill.sh` builds it from this source with a copy of the tool inside (`scripts/`), and a zip | Both read the same kind of folder: a `SKILL.md` with a name and a description. A folder that stands on its own can be copied to either with nothing else to install. Built, not kept twice, so the two copies cannot drift |
| D20 | For the browser, the tool hands out one message at a time (`begin`, `next`, `record`, `finish`) and sends nothing itself. The run is a file in a folder, so a run that stops part-way carries on | The agent's job is then small and the same every time: type what it is shown, bring back what it read. Everything that needs to be exact (which messages, the word lists, the counts, the report) stays in code that is tested |
| D21 | A reply only ever reaches the tool as a file. The agent's own reason is limited to letters, digits, spaces and plain punctuation | A reply is hostile text, and an agent that pastes it into a command line hands it to a shell. This is the one new way in that the browser route opens |
| D22 | The agent that typed a message may give its own reading of the reply (held, gave way, unsure). It is treated exactly like the second-model judge: a known word or nothing, able to add a concern, never able to clear a word-list failure | It is a model reading every reply for nothing extra, which catches what word lists miss. But it has just read text written to talk models round, so it gets no more trust than D9 gives |
| D23 | The run file is checked again each time it is read, and at the end the messages and word lists are read from the packs, not from the run file | The run file sits in a folder an agent writes to. A changed file must not be able to bring its own word lists or pass off a different message |
| D24 | A system with no way to start a new conversation gets everything in one (`--one-conversation`): ordinary messages first, voice-changing attacks last, and the report says so at the top | Some systems give one conversation per sign-in. A rough result with a plain warning is better than no result. Honest messages go first while the conversation is clean |
| D25 | In a browser the two attacks that ask for script back (`core-mar-01`, `core-mar-03`) are left out unless asked for | Script sent back to a page that shows replies unsafely would run in the tester's signed-in browser |
| D26 | The practice chatbot has a chat page | So the skill can be tried, and was tried, without touching a real system |
| D27 | An attack is marked with a risk by name (`prompt-injection`), not by number. The map uses the 2026 edition and shows each risk's 2025 number beside it | OWASP renumbered six of the ten in August 2026 and renamed one. In November 2026 OWASP's own list page still showed 2025, so people will know either. The 2026 titles were read from two write-ups that agree, because OWASP's page for it is a download only: `owasp.py` says so and is the one place to correct |
| D28 | The map always shows all ten risks. One with nothing sent says "none", one that no message can test says "cannot", and under the table it says a clean row is not a risk passed and that the agentic list is not tested at all | The whole point of the map is to stop a pass being read as OWASP cover. Leaving out the untested rows would do the opposite |
| D29 | Attacks carry each technique in a harmless form: a made-up word, or a request for the system's instructions, in place of a harmful request. Every attack in `recent` names where the technique was reported | The question for a team is whether the technique works on their system. Sending real harmful requests proves nothing more and adds risk. It also keeps this repository from being a collection of working harmful prompts. The names and dates were checked against public write-ups, not every original paper, and the pack says so |
| D30 | Every pack carries the date it was last checked against newly reported attacks, and a report says "the attacks are out of date" when that was more than six months before the run | Without a date a two-year-old pack looks exactly like a new one. The date is only changed by someone who actually did the check |
| D31 | The skill's quick pass is the first two of each kind from `core` and `recent`: 30 messages | A person waiting on an agent typing will not sit through 107 on a first try, and a first run should try the newer techniques as well |
| D32 | The skill is not reworded to get a model past its own refusal. Gemini 4 in Antigravity declined to send attack messages "even with authorization or ownership" (November 2026) and the skill was left as it is | The refusal is the model's rule about the task, not a misreading of the skill: it named the task correctly. Describing the work as something else so that a model does it is what this tool exists to catch, and it would last only until the next model |
| D33 | Nothing that names a real organisation's internal systems or people is in the repository, and a test checks for the ones it knows about. The example pack uses a made-up company | The tool began inside one organisation and was published in November 2026 for anyone to use |
| D34 | The README says a model permitted to do security work is the better choice, and lists where the general-purpose models stood | Whether the skill runs depends on the model more than on the agent. Choosing a model whose rules allow security testing is the honest answer to a refusal, where rewording the skill (D32) is not. The list is dated because it will go out of date |
| D35 | A disguise is a copy of an attack with only what is sent changed. The original's word lists judge the reply. The report counts attacks that got through only in disguise. An attack that is already a disguise, or a reported technique, says `no_variants` and is left alone | The finding worth having is "held as written, got through in base64", which says a filter is reading words and not meaning. Judging by the same lists is what makes the two comparable. Disguising a technique from `recent` would test something other than what was reported |
| D36 | Every attack has a severity of high, medium or low, medium unless the pack says. The report and `compare` lead with high | A report of forty failures that starts with "it talked like a pirate" buries "it gave out another user's data". Three levels, set by hand, is as much precision as there is |
| D37 | `compare` matches two runs by id and sorts every message into worse, fixed, still wrong or still right. It ends with exit code 1 when anything got worse, and says that one message changing sides is not proof | "Did my change help, and did it break anything" is the question after the first report. The warning is there because a model's answers vary and a pipeline will otherwise fail on noise |
| D38 | Planted documents: nine files, each with an ordinary body holding a made-up reference number, and a harmless instruction hidden a different way, with a made-up marker that is new for every file and every time. The Word and PDF files are written by hand with the standard library | An instruction in a document is the route most often reported against systems that read files, and nothing here reached it. A new marker each time means an old report cannot be mistaken for a new result. Writing the files by hand keeps D1 |
| D39 | An attack that depends on something the system must find first carries `reached_if`. When the reply shows no sign of it, the result is "not reached", which is neither held nor failed, is not counted as sent in the OWASP map, and is shown as "Tested nothing" | Without it, a system that never read the planted file would score a clean pass. That is the most misleading result this tool could give |
| D40 | An attacker that adapts works towards open goals kept in packs, all harmless. It is told to pursue the goal as written and never to ask for anything harmful. It gets a set number of messages in one conversation and stops at the first reply that gives way. Any reply that gave way counts. If the attacker model declines, the goal is marked not tried and nothing is sent | A fixed list only finds what is on it. Keeping the goals in packs means a person reads and approves what is being attempted, which a free-roaming attacker would not allow. An attacker's refusal sent on as a message would be noise recorded as a test |
| D41 | On the chat page the agent that types is the attacker. It is given the same rules, writes its own messages, and brings back the whole exchange as a file | There is no second model on that route, and the agent is already there. The exchange is hostile text like any reply, so it comes in as a file (D21) |
| D42 | The README says why there is no library of harmful prompts, names the open tools that have one, and says where each differs from this | People will ask why it is so small, and some need what the others do. Sending them there is more useful than pretending to cover it |
| D43 | The cost attacks are probes for a missing limit, never a flood. Each is one bounded request. The largest message is 250,000 characters, the burst is 30 requests one after another, and a pack that asks for more than 300,000 or 60 is refused. Nothing is sent at the same time as anything else | The tool is run against systems that cost real money, by people who may not expect a bill. Whether a limit exists can be found with one request. Finding out how much damage its absence allows is the attack itself, and is not this tool's job |
| D44 | A cost attack is judged by measurement: how long the reply was, how long it took, whether the end of a large message was read, whether a burst was all answered. An error that says "too large" or "slow down" is the system holding. A timeout or a server error is the system failing, not an error in the run. For every other attack an error stays an error | There is no word that shows a system spent too much. And for these attacks the usual reading of an error is backwards: the refusal is the limit doing its job, and silence means the request was more than the system could cope with |
| D45 | The cost pack is only run when asked for by name. It is not in the skill's quick pass | It costs more than the others and can make a system slow for other people. Nobody should find that out afterwards |
| D46 | Over 6,000 characters is "a very long reply" unless the target file says otherwise (`long_reply`) | Longer than any honest answer from an assistant with one job, and shorter than a common output cap, so a system that simply writes until it is cut off is caught. A system meant to write at length sets its own figure |
| D47 | The document that is "read a million times" is in two places: as a paragraph in the message (the cost pack), and as a real file of about a hundred pages (`plant --long-document`), with a reference on its last line so that a system which never read it comes out as "tested nothing" | Nothing loops a million times. The cost is each request honoured as far as the system allows: the whole document going in and the longest reply coming out |

## Open

| No. | Question | Notes |
|---|---|---|
| O1 | Assistants that take actions (send mail, change records, call tools) | Judged today only on what they say. Judging what they did needs access to the system, not just its replies. This is OWASP's Excessive Agency and most of its agentic list |
| O2 | Borrow attacks from the open tools (garak, PyRIT, promptfoo)? | Their features were looked at in November 2026 and four were built here (D35 to D41). Their attack lists were not borrowed: most ask for harmful content (D29). The README points to them (D42) |
| O3 | The gaps a chat test could still reach: misinformation (in a system's own pack), and an instruction behind a link the system fetches | Not built. Instructions in files are covered by planted documents (D38) and unbounded consumption by the cost pack (D43) |
| O9 | More on cost: a conversation that grows until every message is expensive, many users at once, and what an assistant's tools and loops spend | Not built. The first is slow and dear to test. The others cannot be seen from the chat |
| O8 | More from the other tools: output a build pipeline understands (JUnit, SARIF), MITRE ATLAS and NIST tags beside OWASP, streamed replies and cookies on the command-line route, attacks generated from a description of the system | Not built |
| O4 | Who checks the packs against new reports, and how often? | The date and the warning exist (D30). Without someone doing the checking, the warning is all that happens |
| O5 | Supply chain, poisoning and vector stores cannot be tested by sending messages. Should the skill carry a short design-review checklist for them? | Not built |
| O6 | The skill runs in Claude. In Antigravity, Gemini 4 declined (D32). Does another model there run it? Does Codex? | Not tried. The Codex instructions in the README are from OpenAI's documentation only |
| O7 | Releases: should the built skill zip be attached to each release, so nobody has to build it? | Not done |
